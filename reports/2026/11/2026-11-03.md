## 今日要点

- **把长程任务做成可检查的工作流。** CoworkOS 将主 Agent、协调运行时、可选子 Agent 和人类复核组合为本地工作环境，并保留任务状态与日志。
- **让约束在每次行动前可见。** intent-anchor 提出将硬约束写入不可变规格、强制工具调用经过网关，并对偏离采取默认阻止的仲裁路径。
- **证据强度须与主张匹配。** CoworkOS 的仓库链接到论文；intent-anchor 明确标注其为 POC，尚无大规模量化评测。本期据此保留各自的边界，不作超出原始材料的性能结论。

## 开源项目

### CoworkOS：为长程、人机协同任务保留状态与复核入口

![CoworkOS 官方 README 横幅：几何字标、桌面工作区和操作系统框架](https://raw.githubusercontent.com/RUC-NLPIR/CoworkOS/main/docs/assets/readme-hero.png)

*图：CoworkOS README 提供的官方横幅。原始来源：[CoworkOS README](https://github.com/RUC-NLPIR/CoworkOS)。*

[CoworkOS](https://github.com/RUC-NLPIR/CoworkOS) 于 11 月 3 日创建，采用 MIT 许可证。维护者将其描述为一个面向长程、有人参与的任务执行环境：主 Agent 负责规划、委派和评估，协调运行时分发并追踪子任务，可选子 Agent 执行有边界的工作；工作区、记忆与执行记录留在本机。README 还提供 macOS 桌面版与 CLI 的安装方式，并链接项目页、演示和论文。

它值得关注，因为“任务可跨天继续、等待或中断后可恢复”是 Agent 从单轮问答进入实际生产工作时的重要工程问题。状态记录和人工审阅使用户有机会检查中间产物，而不是只能接受最终答案。采用前仍应审阅模型服务配置、工具权限和本地数据处理方式；README 的功能描述不等同于对任何场景可靠性的保证。

来源：[GitHub 仓库与 README](https://github.com/RUC-NLPIR/CoworkOS) · [GitHub API 元数据](https://api.github.com/repos/RUC-NLPIR/CoworkOS) · [项目演示](https://coworkos-ai.github.io/showcase.html)

### intent-anchor：把“别偏离目标”做成可执行的故障关闭机制

[intent-anchor](https://github.com/7urb0/intent-anchor) 于 11 月 3 日创建，采用 MIT 许可证，是一个明确标记为非生产级的概念验证。其 README 描述的结构包括：存放硬约束的不可变 `Spec`、记录偏离的 `DeviationLedger`、每次工具调用前重注入目标状态的 `ToolGateway`，以及对缺少证据的偏离请求一律升级人工处理的 `Arbiter`。它还给出多 Agent 交接中显式接受或质疑偏离的机制，并提供测试与示例命令。

这个项目的价值在于把“模型应该持续记住用户意图”拆成可检查的系统职责：哪些约束不可触碰、何时允许例外、例外需要什么证据。它也如实列出局限：目前是 POC，尚未完成真实任务上的约束违反率对照，线性链以外的拓扑也未验证。因此，适合把它视为设计参考或试验基线，而非直接当作生产安全证明。

来源：[GitHub 仓库与 README](https://github.com/7urb0/intent-anchor) · [GitHub API 元数据](https://api.github.com/repos/7urb0/intent-anchor)

## 趋势 / 编辑简评

今天的两项开源工作从不同方向指向同一件事：长程 Agent 的关键不只是生成质量，还有“过程是否可见、可恢复、可拒绝”。CoworkOS 更偏向把复杂工作组织为人可介入的持续项目；intent-anchor 更偏向为目标与例外建立机械检查点。实践中，二者共同提示了一个优先级：在扩大自治度前，先定义任务状态如何保存、哪些约束不能绕过，以及谁能审核例外。
