## 今日要点

- **隐私审计从扫描走向事务化修改。** `repo-airgap` 明确区分静态候选与恶意判定，要求人工选择后才生成精确补丁，并保留 manifest、校验与回滚记录。
- **评审 Agent 需要“人在回路”。** `herdr-redline` 的 Council review 只把发现放入草稿，最终由人接受、编辑或丢弃；这比让模型直接向代码托管平台发评论更可控。
- **基础设施开始暴露线程级生命周期 API。** Codex 的 managed prewarming 预先准备默认云环境线程，返回线程身份和解析设置，但文档也提示失败时可能留下调用方未拿到 ID 的已准备线程。

## 开源项目

### repo-airgap：为 Agent 代码库做本地隐私与离线就绪审计

![repo-airgap 官方 README 工作流预览](https://raw.githubusercontent.com/Hero-all/repo-airgap/main/assets/workflow-preview.svg)

*图：repo-airgap README 中的官方工作流预览，展示扫描、审阅、计划、应用、验证与回滚路径。原始来源：[repo-airgap README](https://github.com/Hero-all/repo-airgap#workflow)。*

[repo-airgap](https://github.com/Hero-all/repo-airgap) 于 2026-11-04 创建，采用 MIT 许可证。项目提供 Python CLI 与 Agent Skill：扫描源码中的可选外联、遥测、推广 UI、运行时下载和离线开关，结果只作为候选证据；审阅者明确选择后，工具才生成精确的可逆修改计划，并支持验证、报告和回滚。README 还说明扫描阶段不调用远程模型/API、不执行目标代码，并列出对静态分析、代理观测和许可证启发式的限制。

它值得关注，因为 Agent 生态正在把大量第三方仓库、Skill 和 MCP 工具接入执行链。把“发现外联点”“决定是否修改”“应用后验证”拆成有哈希和回滚记录的步骤，有助于审计自动化带来的隐私风险；不过它不能证明运行时绝无网络流量，关键流程仍需在真实网络隔离环境中复核。

### Herdr Redline：把代码评审、流水线与 Agent 放在同一 worktree

![Herdr Redline 官方 README 评审面板截图](https://raw.githubusercontent.com/iampedii/herdr-redline/main/preview.png)

*图：Redline README 提供的评审面板截图，展示终端与变更、Council 发现并排呈现。原始来源：[Redline README](https://github.com/iampedii/herdr-redline)。*

[herdr-redline](https://github.com/iampedii/herdr-redline) 于 2026-11-04 创建。它是 Herdr 的一个 mod，面向 GitHub Pull Request 和 GitLab Merge Request：在独立 git worktree 中启动 Claude Code、Codex、Council review 或 shell，整合请求概览、流水线日志、评论线程、提交和差异查看。Council 结果以可接受的草稿呈现；GitHub 评论在提交前保留在本地，GitLab 则使用服务端 draft note。项目 README 也明确提示，合并、草稿切换、标签/评审人编辑和作业重试等写操作尚未在真实请求上完整验证。

它值得关注，因为“生成代码”与“让代码可合并”是两条不同链路。独立 worktree 防止评审污染开发目录，逐行草稿和人工提交则为 Agent 提供了可追责的最后一道闸门；项目仍较新，使用前应先在无关请求上验证写操作。

来源：[GitHub 仓库与 README](https://github.com/iampedii/herdr-redline) · [GitHub API 元数据](https://api.github.com/repos/iampedii/herdr-redline)

## 论文 / 研究

### Adversarial Speculative Reasoning：把 speculative decoding 变成长程推理的精度分配器

[论文：Adversarial Speculative Reasoning Improves Long Horizon Agents](https://arxiv.org/abs/2611.05345) 于 2026-11-03 18:45 UTC 提交 arXiv。作者研究长程 Agent 中 speculative decoding 的数值噪声：验证窗口的 draft 接受结果在多步之后会改变输出分布，因此影响 Agent 任务成功率。方法是在关键推理位置训练 draft model 主动产生会被拒绝的候选，使验证在这些位置重新由 target model 以更高精度采样；摘要称仅训练托管参数的 0.06%–0.28%，在复杂 Agent 编码基准上提升端到端成功率。

这项工作的启发是：推测解码不必只追求吞吐，还可以按推理重要性分配上下文精度。报告保留论文的“摘要级”结果，不把尚未独立复现的基准提升当作生产保证；读者应进一步检查完整实验设置、模型和代码可得性。

## 业界动态

### OpenAI Codex：managed thread prewarming

OpenAI Codex 官方仓库在 2026-11-04 的提交 [010520d](https://github.com/openai/codex/commit/010520de766c4f23f45a540b4c4d5c6c67fbf7ff) 为 cloud client 增加 `Client::prewarm_default_thread`。该 API 可按默认或指定模型/提供商预热普通 coding thread，返回线程身份和解析后的设置，并保留原生线程元数据；实现对预热请求不自动重试，也不清理失败后可能已准备好的线程。提交同时加入沙箱策略缺失、设置解析、序列化和敏感调试输出的测试。

这不是面向终端用户的模型发布，而是 Agent 平台的生命周期能力。它把“准备运行环境”和“激活/执行线程”分开，为客户端提供更早的配置检查点，同时把幂等性和不确定结果处理明确暴露给调用方。

## 趋势 / 编辑简评

今天的信号共同指向“Agent 的控制面”：代码库需要知道何时会外联，评审需要知道谁批准了哪一行，云线程需要知道何时创建、何时激活以及失败后状态是否未知。下一阶段的竞争点可能不只是模型能力，而是这些控制面能否提供可检查的证据、可恢复的状态和明确的人工接管点。对于团队落地，优先级应是先记录边界与失败语义，再扩大自动执行范围。
