## 今日要点

- **可观测性正在从日志检索走向团队操作界面。** `whatsmyagentdoing` 直接读取本机 Claude Code、Codex 与 Gemini CLI 的会话日志，并把状态推送到本地浏览器；其关键边界是只绑定 `127.0.0.1`，不会把提示词或日志上传到外部服务。
- **安全 Agent 的职责切分更具体了。** Argus 的公开设计将 Agent 定位为只读调查与提出操作请求，执行仍受策略、审批、演练与回滚约束。这是值得借鉴的控制面模式，但其「已实现」功能列表仍应由采用方自行审计和压测。
- **研究关注点从“会不会调用工具”转向“何时信任”。** 一项预印本训练小模型做跨工具库选择；另一项将长期记忆是否需要重验，和即将执行的行动风险绑定。

## 开源项目

### whatsmyagentdoing：把本地 Agent 会话变成实时协作视图

![whatsmyagentdoing 官方仓库预览](https://opengraph.githubassets.com/1/Charonyuu/whatsmyagentdoing)

*图：whatsmyagentdoing 的 GitHub 官方仓库预览。原始来源：[Charonyuu/whatsmyagentdoing](https://github.com/Charonyuu/whatsmyagentdoing)。*

[whatsmyagentdoing](https://github.com/Charonyuu/whatsmyagentdoing) 创建于 10 月 23 日。维护者将其描述为可通过 `/myoffice` 打开的本地技能：它读取 Claude Code、Codex 和 Gemini CLI 写入磁盘的会话日志，经 Server-Sent Events 在浏览器中显示思考、工具运行、等待用户、完成等状态，并提供 2D、3D 与列表视图。README 明确称服务仅绑定 `127.0.0.1`、没有运行时依赖，且支持 `--private` 隐去提示词、回复和标题。

它值得关注，不是因为把 Agent 做成“办公室”界面，而是把多会话调度里最常见的盲点——阻塞、等待批准、子 Agent 状态——带到一个低摩擦的本地观察面。使用时仍要注意：它依赖各 CLI 的日志格式，而这些格式不是公开 API；共享屏幕或录制前应启用隐私模式，并审阅本地日志访问范围。

来源：[GitHub 仓库](https://github.com/Charonyuu/whatsmyagentdoing) · [GitHub API 元数据](https://api.github.com/repos/Charonyuu/whatsmyagentdoing) · [README 隐私与工作原理](https://github.com/Charonyuu/whatsmyagentdoing#how-it-works)

### Argus：用独立策略边界约束安全运营 Agent

![Argus 官方仓库预览](https://opengraph.githubassets.com/1/thomasunise/argus)

*图：Argus 的 GitHub 官方仓库预览。原始来源：[thomasunise/argus](https://github.com/thomasunise/argus)。*

[Argus](https://github.com/thomasunise/argus) 于 10 月 24 日公开，采用 MIT 许可证。其 README 将其定位为自托管安全运营平台，并称七类专业 Agent 只使用只读工具做分诊、调查与威胁搜寻；它们可以提出修复建议，但不会直接执行。文档描述的写入路径是先形成待处理的 `ActionRequest`，再由独立的 action broker 按策略、审批、dry-run、影响范围上限与自动回滚处理；自动化能力默认关闭。

这一结构值得团队借鉴：把“模型给出建议”和“系统产生外部影响”拆成可审计的两个权限域。需要谨慎的是，上述功能覆盖与测试数量属于项目维护者的 README 声明；在接入云、身份或端点控制面前，应独立验证连接器权限、租户隔离、回滚演练和告警链路。

来源：[GitHub 仓库](https://github.com/thomasunise/argus) · [GitHub API 元数据](https://api.github.com/repos/thomasunise/argus) · [威胁模型文档](https://github.com/thomasunise/argus/blob/main/docs/THREAT-MODEL.md)

## 论文 / 研究

| 论文 | 核心内容 | 为什么值得关注 |
| --- | --- | --- |
| [Training Small Language Models for Transferable Tool Selection](https://arxiv.org/abs/2610.31483) | 作者研究让经强化学习后训练的小型开放模型，从大规模工具库中为复杂指令挑选所需工具；论文报告在 ToolBench 上，所述 Qwen3-8B 配置超过一个更大的对比模型，并测试了对不同检索器与新工具语料的迁移。 | 工具选择并非简单的语义检索：工具多、上下文有限时，系统还要判断“哪些工具真的必需”。结果有待独立复现，但把选择器与执行模型分层，是控制成本和上下文长度的实用方向。 |
| [When Is a Memory Safe Enough to Act On?](https://arxiv.org/abs/2610.31446) | 该工作提出“行动条件化的记忆核验”：是否重验一条记忆，取决于即将执行的行动后果、核验成本及其是否可能改变下一步；文中以 AMV-Guard 在 ToolSandbox 和迁移实验中评估。 | 长期 Agent 的记忆并非越新越安全。将地址、权限、金额等事实的复核强度与操作风险绑定，能让“先核验还是直接执行”成为明确的策略，而不是固定提示词。 |

两篇均为 arXiv 预印本，官方记录显示首次提交于 2026-10-22 UTC。表中的实验数字和比较结论来自论文作者，尚不应外推为所有模型、工具集或真实部署环境的保证。

### LangChain Core 1.7.0 发布：框架版本更新仍应以依赖锁定和回归为准

LangChain 于 10 月 22 日发布 [`langchain-core==1.7.0`](https://github.com/langchain-ai/langchain/releases/tag/langchain-core%3D%3D1.7.0)。官方 release 页面将其列为核心包的新版本；与此同时，仓库在此前数日也发布了 `langchain==1.4.7` 和 `langchain-core==1.6.13`。对 Agent 应用而言，核心依赖的小版本和主版本更新会触及消息、工具、流式事件及回调等集成边界；即便 release 摘要不长，升级也应通过锁定版本、检查变更记录，并对工具调用、stream parser 与 tracing 做回归验证。

## 趋势 / 编辑简评

今天最清晰的主线是 **“把 Agent 纳入可观察、可约束、可复核的系统”**。本地仪表盘降低了协作中的状态不透明；安全运营把执行权从模型建议中剥离；研究则进一步追问在工具爆炸与长期记忆下，系统何时该选择、何时该核验。对团队而言，下一步不妨优先定义三条可测边界：谁能看到会话内容、谁能批准外部动作、哪类高后果操作必须重新取证。
