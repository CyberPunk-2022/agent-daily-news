## 今日要点

- **循环并不是“胶水代码”那么简单。** `agentloop` 把迭代上限、成本上限、重复调用检测和完整执行 trace 作为运行时的默认组成部分；这让团队能从一开始就为失控循环和成本异常留下控制点。
- **世界模型被用于决定“要不要先看一眼未来”。** RynnUnify 的论文/代码把视频生成结果反馈给推理器，并训练路由策略选择直接回答或生成辅助轨迹；这是把 world model 作为 Agent 证据工具的一种具体路线。
- **可靠性改进常落在失败分支。** Claude Code v2.1.310 对 MCP 无人响应时的超时提示、过长上下文后的压缩、后台清理等路径进行了修复，提醒集成方对异常工具调用和长会话做回归测试。

## 开源项目

### agentloop：面向 Go 的可预算、可追踪工具调用循环

[agentloop](https://github.com/smhanov/agentloop) 于 10 月 25 日创建，采用 MIT 许可证。维护者将它定位为 Go 的 Agent 运行循环：向模型发起请求、执行工具调用、回填结果直至产出回答，同时提供预算、hooks、skills 与 tracing。README 称每次 `Ask` 会返回文本、完整工具执行轨迹、消息记录和 token/成本使用量；其示例还展示了工具调用数量、步数和成本上限，以及重复调用检测与流式 watchdog。

值得关注的是其取舍：通过 sister project `llmhub` 适配多个模型供应商，却将 Agent 控制循环保留在一个 Go 库中。对已有 Go 服务、CLI 或定时任务，这是一条降低部署复杂度的路线。不过“默认安全”不等于替业务授权：实际采用仍应为 shell、网络和写操作配置最小权限、确认机制与独立审计。

来源：[GitHub 仓库](https://github.com/smhanov/agentloop) · [GitHub API 元数据](https://api.github.com/repos/smhanov/agentloop) · [包文档](https://pkg.go.dev/github.com/smhanov/agentloop)

### RynnUnify：让具身推理器在必要时调用视频世界模型

![RynnUnify 官方项目概览](https://raw.githubusercontent.com/alibaba-damo-academy/RynnUnify/main/assets/teaser.png)

*图：RynnUnify 的官方项目概览，展示具身理解、视觉规划、Agent 推理与机器人动作的连接。原始来源：[项目 README](https://github.com/alibaba-damo-academy/RynnUnify#introduction)。*

[RynnUnify](https://github.com/alibaba-damo-academy/RynnUnify) 是阿里巴巴达摩院于 10 月 25 日公开、采用 Apache-2.0 许可证的项目。项目说明中提出一个由 8B 自回归 Reasoner 和 8B rectified-flow 视频 Generator 组成的 16B Mixture-of-Transformers 架构，用交错的视觉—语言推理与视频预测支持具身理解、空间定位及长程视觉规划。其 World-Action Model（WAM）扩展则尝试把世界表征连接至机器人控制。

其 Agentic Interleaved Thinking 部分尤其值得留意：作者使用 BCPO，让 Agent 在直接推理与请求生成视觉证据之间选择；生成器保持冻结，仅更新 Agent。开源了模型条目、训练/评测接口与论文，降低了复现实验门槛。需要保留边界的是，README 内的 benchmark 图表和实机效果均为作者报告，硬件、任务分布和安全约束不同的部署不应据此直接外推。

## 论文 / 研究

### RynnUnify: Towards Unified Embodied Brain

[论文（arXiv:2610.32965）](https://arxiv.org/abs/2610.32965) 与同名代码仓库同步公开。论文将自回归推理器和视频生成器通过 joint attention 结合：推理器提出下一子任务、视觉描述和时长，生成器根据场景记忆和近期运动预测视频片段。作者进一步以 Branch-Conditional Policy Optimization（BCPO）比较直接与生成辅助的轨迹，并学习何时请求生成结果。

这一思路的重要处不只在“生成视频”，而在于把生成成本与决策价值绑定：若预测画面不会改变动作，Agent 应直接作答；若未来状态会影响抓取、路径或多步规划，再请求视觉证据。论文为预印本，且其公共基准与真实机器人结论尚待独立复现；采用者还需要评估生成延迟、预测误差累积和实体执行前的安全校验。

来源：[arXiv 官方记录](https://arxiv.org/abs/2610.32965) · [论文 PDF](https://arxiv.org/pdf/2610.32965) · [代码与评测说明](https://github.com/alibaba-damo-academy/RynnUnify)

## 业界动态

### Claude Code v2.1.310：为监控、长会话和 MCP 超时补齐运行时细节

Anthropic 于 10 月 23 日发布 [Claude Code v2.1.310](https://github.com/anthropics/claude-code/releases/tag/v2.1.310)。官方 release 称新增了 Monitor 工具和 plugin monitors（覆盖 Bedrock、Vertex、Foundry 及关闭 telemetry/非必要流量的场景）；同时修复了密集文本导致“Prompt is too long”后的过度保留上下文问题、部分后台清理误删近期文件的问题，并在非交互会话的 MCP 工具超时且 elicitation 未获响应时，返回“未收到回答、不要重试”的明确提示。

这类改动值得集成方关注：一个 Agent 运行时不仅要显示成功工具调用，更要区分等待人类输入、服务端超时与可安全重试的失败。升级前建议在受控环境回归 MCP 交互、长上下文压缩、后台清理和自定义网关连接；release 中描述的行为是该版本的官方声明，环境差异仍可能影响实际表现。

来源：[Claude Code v2.1.310 官方 Release](https://github.com/anthropics/claude-code/releases/tag/v2.1.310) · [Claude Code Releases](https://github.com/anthropics/claude-code/releases)

## 趋势 / 编辑简评

今天的共同主题是 **“把 Agent 的下一步变成可控制、可观察、可说明的选择”**：agentloop 将循环预算和 trace 显式化；RynnUnify 训练模型决定是否花成本生成未来证据；Claude Code 则完善监控和失败分支。对团队来说，下一轮架构评审可以优先问三个问题：一次工具调用的预算归谁管？失败时系统能否区分等待、超时和拒绝？哪些高后果动作必须在执行前额外取证？
