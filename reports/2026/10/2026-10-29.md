## 今日要点

- **本地工具与外部动作需要分层。** topopt 的本地计算、Plugboard 的统一外部连接、Injection sentinel 的工具后检查，分别覆盖了 Agent 的计算、授权和输入三个层面。
- **“审批”是产品能力，也是边界。** Plugboard 将发送、删除、分享与邀请列为需审批动作；其 README 的承诺需要在具体部署中按服务和策略验证。
- **安全钩子不是万能过滤器。** Injection sentinel 明确写出了误报和漏报限制；从不可信网页取得的信息仍应当作数据处理，避免给 Agent 过宽的网络、密钥或写入权限。

## 开源项目

### topopt：让 Agent 发起拓扑优化的本地 MCP 服务

![topopt 官方 README 的足桥优化过程动图：在仪表盘中逐步生成受力结构](https://raw.githubusercontent.com/chartergroup/topopt/main/docs/media/hero.gif)

*图：topopt README 的官方录屏，展示一个足桥示例在仪表盘中的优化过程。原始来源：[topopt README](https://github.com/chartergroup/topopt#topopt)。*

[topopt](https://github.com/chartergroup/topopt) 于 10 月 29 日创建公开仓库，采用 MIT 许可。维护者将其描述为可供 Claude、Codex、Cursor 等 MCP 客户端使用的本地拓扑优化服务器：用户可提供 STL、草图或文字约束，工具生成可打印的 STL 结果。README 标记项目仍处于 early 状态，并列出 macOS Apple Silicon / Linux x86_64 与内存等运行条件。

同日发布的 [v0.5.1](https://github.com/chartergroup/topopt/releases/tag/v0.5.1) 官方说明包含 Pillow 13.0.0 更新（称修复 41 个已知公告项）、封闭空腔保留和 GPU 内存保护相关修复。它值得关注，是因为它把物理设计计算以 MCP 工具形式交给 Agent 调度；但载荷、边界条件和最终可制造性都不能仅凭 Agent 输出确认，仍需要领域人员审查。

来源：[GitHub 仓库与 README](https://github.com/chartergroup/topopt) · [GitHub API 元数据](https://api.github.com/repos/chartergroup/topopt) · [v0.5.1 官方 Release](https://github.com/chartergroup/topopt/releases/tag/v0.5.1)

### Plugboard：为多个 Agent 集中管理 MCP 上游、审批与日志

![Plugboard 官方 README 动图：多个 Agent 经由一个网关连接服务，并在发送邮件前请求批准](https://raw.githubusercontent.com/mikecann/plugboard/main/docs/media/plugboard.gif)

*图：Plugboard README 的官方动图，展示多 Agent 通过网关访问服务以及发送前审批。原始来源：[Plugboard README](https://github.com/mikecann/plugboard#plugboard)。*

[Plugboard](https://github.com/mikecann/plugboard) 于 10 月 29 日创建公开仓库，采用 MIT 许可。其 README 将它定位为运行在 macOS 上的 MCP 网关：一次登录 Notion、Gmail、Google Calendar、Sentry 等服务后，可为 Claude Code、Codex 等客户端提供统一入口；每个 Agent 使用独立 token，并记录调用。

维护者称发送、回复、删除、分享和邀请等不可逆或会触达他人的操作需要在审批页确认，而读取与普通页面编辑不在这一列表。这个取舍值得讨论：网关可集中审计和授权，但不同服务的工具语义、部署方式和规则决定了审批覆盖是否充分。使用者应先在测试账户核对实际权限，并保护好宿主机上的 token 与管理页面。

来源：[GitHub 仓库与 README](https://github.com/mikecann/plugboard) · [GitHub API 元数据](https://api.github.com/repos/mikecann/plugboard)

### Injection sentinel：在工具调用后提示网页提示注入风险

[Injection sentinel](https://github.com/CodeCombustion/injection-sentinel) 于 10 月 29 日创建公开仓库，采用 MIT 许可。它提供 Claude Code 与 Codex 的 `PostToolUse` 钩子，按 README 所述可识别诱导 Agent 外传个人数据、系统指令、工具信息或密钥的网页文本，也会标记要求忽略指令等覆盖尝试。命中后它向 Agent 会话提示“将文本视为数据”、记录经过脱敏的证据，并为部分数据收集场景生成待人工审阅的通知草稿。

该项目把提示注入处理放到实际开发工作流里，因而值得关注；同时维护者明确说明它是模式匹配，可能漏检或误报，浏览器工具也不总会把来源 URL 交给钩子。它应作为纵深防御的一环，而非授权 Agent 处理敏感数据或自动对外发信的理由。

来源：[GitHub 仓库与 README](https://github.com/CodeCombustion/injection-sentinel) · [GitHub API 元数据](https://api.github.com/repos/CodeCombustion/injection-sentinel) · [安装与限制说明](https://github.com/CodeCombustion/injection-sentinel#limits)

## 趋势 / 编辑简评

今天更像是 **Agent 工具链的“控制面”正在成形**：topopt 让 Agent 触达专业计算，Plugboard 将跨服务身份和审批收拢到网关，Injection sentinel 则尝试在不可信内容进入上下文后补上一道防线。三者的共同点不是更长的自主执行，而是为执行加上约束、日志与人工接管点。对团队来说，优先级应是先明确数据边界与可撤销动作，再扩展工具数量；对任何涉及工程安全、对外通信或敏感凭据的任务，都应保留人类复核。
