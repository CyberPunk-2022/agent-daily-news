## 今日要点

1. **本地 Agent 基础设施开始把“能连上模型”与“能控制数据和权限”一起设计。**AstrLink 把凭据、协议转换、路由与本地规则放在网关；OpenCapX 则把能力调用、插件和命令拦截置于桌面端控制面。
2. **记忆不应只以“模型复述了什么”来评分。**DolphinBench 让 Agent 在模拟应用中完成操作，并对工具调用与评分证据留档，使长期记忆的有效性更接近实际工作流。
3. **可用性声明仍须与验证边界并列阅读。**三项材料均来自项目方公开仓库；未发布的安装包、未签名构建、未审计的权限模型，以及论文外的基准结果，都不应直接外推为生产保证。

## 开源项目

### AstrLink：在本地网关中统一 Agent 的模型路由与隐私策略

![AstrLink 官方标志](https://raw.githubusercontent.com/Calcium-Ion/AstrLink/main/assets/branding/astrlink-logo.png)

*图：AstrLink 官方仓库中的标志。原始来源：[Calcium-Ion/AstrLink](https://github.com/Calcium-Ion/AstrLink)。图片无法加载时，请以仓库 README 为准。*

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-22 04:20 UTC**，许可证为 Apache-2.0；本期采集时为 19 stars。
- **项目：**[Calcium-Ion/AstrLink](https://github.com/Calcium-Ion/AstrLink)。
- **项目自述：**这是面向 macOS、Windows 和 Linux 的桌面应用。它为本地 Agent 暴露 OpenAI Responses、Chat Completions、Anthropic Messages 与 Gemini 兼容端点，可集中连接订阅或 API 提供方、配置别名与重试，并按规则或本地模型检测、告警、阻断或脱敏敏感内容。
- **为什么值得关注：**Agent 的模型选择、预算、故障切换与数据暴露往往分散在客户端配置中。AstrLink 尝试把这些决策集中到一个可查看请求记录的本地入口；特别是“先本地处理、再按策略发往上游”的分层，对同时使用多家模型服务的团队有实际参考价值。
- **采用提示：**项目明确表示仍处于早期开发阶段，尚无官方安装包；GitHub Actions 构建可能未签名或未公证。README 也说明推理请求仍会发往配置的上游提供方，是否处理到敏感信息取决于启用的策略与检测结果。其自身为 Apache-2.0，但 README 指出包含 RelayKit 时还须履行该依赖的 AGPL-3.0 义务；部署前应分别审阅许可证、构建来源和实际网络流量。

### OpenCapX v0.1.0：把桌面能力与 Agent 权限判断放在同一个本地核心

![OpenCapX 官方架构图：Agent 通过 MCP 网关和 PreToolUse hook 接入 Rust 核心](https://raw.githubusercontent.com/opencapx/OpenCapX/main/public/diagram.jpeg)

*图：OpenCapX README 中的系统架构图。原始来源：[opencapx/OpenCapX](https://github.com/opencapx/OpenCapX)。图片无法加载时，请以仓库 README 为准。*

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-22 09:34 UTC**，许可证为 Apache-2.0；官方 [v0.1.0 Release](https://github.com/opencapx/OpenCapX/releases/tag/v0.1.0) 发布于 **09:58 UTC**。
- **项目：**[opencapx/OpenCapX](https://github.com/opencapx/OpenCapX)。
- **项目自述：**该跨平台桌面层可通过 MCP 为 Agent 提供视觉、语音、剪贴板、浏览器读取和媒体等能力，并用 Rust 核心处理能力路由、两层权限判断与活动记录。扩展被描述为经签名的独立 JSON-RPC 子进程；`PreToolUse` 钩子可将部分 Agent 的 shell 调用重写到用户配置的执行器。
- **为什么值得关注：**当 Agent 从编辑文件延伸到调用桌面资源时，能力发现、插件供应链、授权和审计会相互耦合。OpenCapX 的设计把 UI 与安全控制分离，并把插件隔离和权限声明作为一等概念；即使不采用该项目，这也是评估本地 Agent 扩展架构时应逐项询问的控制点。
- **安全边界：**项目明确写明它只负责路由，不替用户配置的 sandbox、代理或容器作安全裁决；命令规则的项目级文件也需显式信任。macOS 构建尚未代码签名或公证。上述机制和安全主张均来自项目方，实际权限隔离、签名校验和命令重写应在目标环境中独立测试。

### DolphinBench：用工具执行结果而非记忆复述评估长期 Agent 记忆

![DolphinBench 官方图标](https://raw.githubusercontent.com/mem0ai/dolphinbench/main/website/public/brand/dolphinbench-icon-512.png)

*图：DolphinBench 仓库中的官方图标。原始来源：[mem0ai/dolphinbench](https://github.com/mem0ai/dolphinbench)。图片无法加载时，请以仓库 README 为准。*

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-22 03:34 UTC**，许可证为 Apache-2.0；提交记录显示项目方于 **05:51 UTC** 提交“Add final DolphinBench release”。
- **材料：**[mem0ai/dolphinbench](https://github.com/mem0ai/dolphinbench)（数据集、模拟应用、运行器、评分器、参考代码与官方运行记录）。
- **项目自述：**该基准包含 3 位模拟用户、每人约 50 万 token 的历史，以及 600 个需调用工具完成的测试。它要求 Agent 先处理历史、保留记忆检查点，再在独立会话和应用状态中完成任务；评分同时保留对话、工具结果、模型设置、用量和评分证据。仓库还描述了带历史与不带历史的对照认证流程。
- **为什么值得关注：**“记忆”在演示中容易被简化成检索到一句正确文本，而真实助手需要把日期、收件人、参数或文档内容转成正确操作。DolphinBench 将衡量目标转向任务动作与可审计轨迹，并公开多种配置的运行材料，这使比较 Agent memory 实现时更容易检查复现实验的输入和成本。
- **解读边界：**该仓库是当天公开的研究基准和实现材料，本期没有找到可由 arXiv 官方 API 核验、且提交时间落在 2026-09-22（UTC）的 Agent 相关论文。因此不把该项目表述为已完成同行评审的论文结论；其模拟用户、任务设计、评分器与所报告配置的外推性仍需独立复现和审阅。

## 趋势 / 编辑简评

今天的三项材料从不同层面回答了同一个工程问题：当 Agent 拥有跨会话记忆、模型路由和桌面能力后，团队如何证明它做对了事，又如何限制它在错误时造成的影响？DolphinBench 强调行动及其证据，AstrLink 将数据规则与上游路由放到本地入口，OpenCapX 则将能力和权限判断放到核心运行时。

这条路线并不意味着“本地”天然安全。网关仍可能向上游发送内容，命令改写仍依赖最终执行器，评测也依赖场景与评分器假设。更可靠的采用顺序应是：先厘清数据流、信任边界和撤销机制，再用小范围、可复核的任务验证记忆和工具行为，最后才扩大自动化权限。
