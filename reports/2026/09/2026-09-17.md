## 今日要点

1. **评审成为 Agent 的持续环节。**Jev Review 只输出结构化质量信号，不直接改代码，保留主 Agent 的责任边界。
2. **浏览器自动化转向连续运行时。**Jev Browser 让选择器在观察循环内工作，但页面文本会发送给远端服务，需评估数据边界。
3. **垂直文档工作流强调事实与人工闸门。**BidCraft 把标段隔离、全局事实和逐章思路前置，避免“一键生成”掩盖关键数字错误。
4. **研究开始量化多 Agent 的真实成本。**agentic-eCAL 指出，额外推理与上下文处理可能比 Agent 间文本传输更主导能耗。

## 开源项目

### Jev Review：为 Claude Code、Codex、Cursor 和 OpenCode 提供本地质量检查

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-17 05:24:51 UTC**，MIT 许可证，34 Stars（采集时快照）。
- **项目：**[NiazMorshed2007/jev-review](https://github.com/NiazMorshed2007/jev-review)。
- **项目自述：**本地 Node.js MCP stdio 服务，围绕正确性、复杂度、可变更性、模块化、测试和安全等维度调用 Jev；API Key 保存在本机，仓库没有托管后端、数据库或作者代理。工具返回 typed Score、Choice、Noul 决策，并比较前后评估，不合成单一总分。
- **为什么值得关注：**它把“代码看起来不错”拆成可重复的检查点，适合在实现切片、修复反馈和交付前做多次评估；同时明确 Agent 仍负责改代码，减少自动评审越权。
- **采用提示：**远程请求仍会把选定的代码上下文发往 Jev API；应先审阅供应商数据政策，并把结果与项目测试、人工审查结合。

### Jev Browser：在连续循环中选择浏览器元素

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-17 03:45:16 UTC**，MIT 许可证，19 Stars（采集时快照）。
- **项目：**[vlad-terin/jev-browser](https://github.com/vlad-terin/jev-browser)。
- **项目自述：**Agent 先制定有界计划，运行时反复执行 snapshot → Jev 选择 → 浏览器动作 → 验证；支持多标签、目标页验证和最多六路候选拆分。README 将其标为实验性、浏览器专用，Codex 适配器是主要测试路径。
- **为什么值得关注：**把每一步元素选择从 Agent 回合中移到连续运行时，可能降低长流程的上下文往返和脆弱性；同时保留需要 Agent 介入的边界条件。
- **风险边界：**页面文本会发送给 TypeSafe；视觉控件、脚本创建的弹窗和非兼容宿主仍可能需要人工协助，不应按通用浏览器自动化能力宣传。

### BidCraft 标书匠：面向工程招标文件的对话式 Agent

![BidCraft 官方 README 工作台截图](https://raw.githubusercontent.com/zeronezer/bidcraft/main/docs/images/screenshots/workspace.png)

*图：BidCraft 官方 README 的虚构演示工作台截图；原始来源：[zeronezer/bidcraft](https://github.com/zeronezer/bidcraft)。图片无法加载时，请以仓库 README 和文字说明为准。*

- **首次公开：**GitHub API 显示仓库创建于 **2026-09-17 03:42:48 UTC**，Apache-2.0 许可证，10 Stars（采集时快照）。
- **项目：**[zeronezer/bidcraft](https://github.com/zeronezer/bidcraft)。
- **项目自述：**Python 3.11 + Vue 3 应用，使用 LangGraph；可解析 PDF/扫描件、隔离标段、提炼历史施组知识页、维护带出处的全局事实表，并通过对话重写章节。README 的演示项目和截图均为虚构资料。
- **为什么值得关注：**它展示了垂直 Agent 的另一条路线：把目录、数字、素材和人工审核建模为显式状态，而不是只优化生成文本的流畅度。
- **采用提示：**运行依赖 MySQL、LLM API 和可选 MinerU；“周期从数周压到数天”是项目方目标陈述，不能视为已验证生产指标。上传真实招标文件前应审查数据留存与第三方 API 边界。

## 论文 / 研究

### agentic-eCAL：衡量边缘-云多 Agent 工作流的能耗

- **论文：**[Where Should Agents Live? Energy-Memory Characterization of Agentic AI for the Edge-Cloud Continuum](https://arxiv.org/abs/2609.18283)（arXiv:2609.18283，2026-09-16 发布）。
- **核心内容：**作者提出 agentic-eCAL，把 prefill/decode 的计算与内存模型、7 层 OSI 传输和多 Agent 拓扑结合，并基于数百个 A100/H100 配置、16 个开放模型和 8 种编排拓扑分析部署位置。
- **关键结果（作者报告）：**在其 5G RAN、城域和光链路设定中，Agent 间文本传输约占工作流能耗的 **0.25%**；额外推理与上下文处理通常更值得优化。
- **为什么值得关注：**它提醒架构团队不要只看网络流量；复制实验前应核对硬件、模型、量化和通信假设，不能把该比例外推到所有 Agent 产品。

### DualViewEval：同时利用结果与过程轨迹压缩 Agent 基准

- **论文：**[Beyond Outcomes: Dual-View Relational Learning for Efficient Agent Benchmarking](https://arxiv.org/abs/2609.18909)（arXiv:2609.18909，2026-09-16 发布）。
- **核心内容：**DualViewEval 从最终得分和轨迹中的六类过程信号共同学习固定大小的任务子集，在五个 Agent 基准上预测完整测试集表现。
- **作者报告：**在 APEX-Agents 和 BFCL 上用 20 个任务实现 24–40 倍压缩；在 SWE-bench Verified 上，相比最强基线 MAE 降低 14.5%–28.2%，Kendall τ 相对提升最高 7.2%。
- **为什么值得关注：**它把“少测一些任务”变成可诊断的基准设计问题；这些数字仍是论文实验结果，落地时需验证任务分布变化和代理过拟合风险。
