## 开源项目

### MCP server for Obsidian：通过本地 REST API 让 Agent 操作 Obsidian vault

![MCP server for Obsidian 在项目 README 中引用的服务器目录卡片](https://glama.ai/mcp/servers/3wko1bhuek/badge)

*图：项目 README 内引用的服务器目录卡片；原始来源：[README.md](https://github.com/vindicare3162/mcp-obsidian/blob/main/README.md)。图片不可用时，请以项目 README 与下方文字说明为准。*

- **首次公开：**GitHub 仓库创建于 **2026-07-28 00:22 UTC**。
- **项目：**[vindicare3162/mcp-obsidian](https://github.com/vindicare3162/mcp-obsidian)（MIT）。
- **项目自述：**这是一个经由 [Obsidian Local REST API](https://github.com/coddingtonbear/obsidian-local-rest-api) 社区插件与 Obsidian 交互的 MCP server。README 列出根目录/子目录枚举、单文件读取、跨 vault 文本搜索、相对标题/块引用/frontmatter 的 `patch_content`、追加内容与删除文件（或目录）等工具；发布版示例使用 `uvx mcp-obsidian`，并要求 `OBSIDIAN_API_KEY`、`OBSIDIAN_HOST` 和 `OBSIDIAN_PORT` 配置。
- **为什么值得关注：**Agent 的知识库集成往往从只读问答开始，但实际工作流很快会需要把会议摘要写回、针对特定标题补充决策、或清理生成物。该项目把这些操作显式拆成独立工具，便于 host 根据“读 / 写 / 删除”实施不同的批准策略与审计。反过来，`delete_file` 和可定位的 `patch_content` 也意味着它不应被视作普通检索连接器：生产使用前应在测试 vault 验证路径范围、备份与冲突处理，并限制 API key 和 MCP client 的可访问范围。
- **采用提示：**README 未宣称事务、版本恢复或细粒度访问控制；这些能力不应被推断为项目已提供。将密钥放入受保护的运行时配置，避免提交到 `.env` 或 Agent 可读取的普通工作区。

## 趋势 / 编辑简评

今天唯一满足来源与时效门槛的条目并不追求替 Agent “知道更多”，而是让它能在一个明确接口内对既有知识库执行动作。值得关注的并非工具数量本身，而是这些动作已经覆盖从读取到不可逆删除的权限跨度。对 MCP 集成而言，一个实用的工程问题是：**每项工具调用能否被清楚地区分、批准、记录与回滚？**把这层边界设计在连接器和 host 中，比事后依赖提示词约束更可靠。
